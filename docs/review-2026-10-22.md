# railway-server review — 2026-10-22

Scope: every `railway-server/` route and park relay module shipped since 2026-09-20
(`git log --since=2026-09-20 -- railway-server`): the calculator absorb rounds (protocols
9–17), `GET /park/calc/due`, `GET /park/calc/progress`, the handheld check, the bonus rail
to roster-server, `POST /park/campaign/keys/grant`, the campaign relay batches, and the AI
grade / appeal / "Talk it through" endpoints. Questions asked of each write path: auth or
identity on the write; can it lower a stored grade, score, rung or mastery; unbounded input
on a public endpoint; 5xx on bad input; read-modify-write races on a student row.

Every item below was read end to end before it was classified. Confirmed findings were
fixed with a test; the rest are listed with the reason they could not be confirmed.

## Confirmed and fixed

### 1. Public calculator reads allocated server state per arbitrary `section` string

- Where: `railway-server/server.js` `GET /park/calc/due` and `GET /park/calc/progress`
  (inline handlers before this commit) → `service.mjs calcDue/calcProgress` →
  `calculator-service.mjs due()/progress()` → `calculator-srs-state.mjs sectionState()`
  (line 19) and `calculator-clears.mjs sectionState()` (line 37).
- What: both routes are public and read-only, but any `section` query string reached the
  stores' `sectionState()`, which creates a permanent Map entry and starts a paged Supabase
  load for that section. One entry and one database read per distinct string, never freed,
  from an unauthenticated GET.
- Fix (commit `e06fe3d`): handlers extracted to `apstat-park/calc-read-routes.mjs`; the
  section is checked against `CLASSROOM_SECTIONS` (`shared-classroom.mjs`: the shared
  classes PeriodB/PeriodE/B/E plus the teacher's PeriodX/X — the same set
  `eligibleLevels` maps) before the park service sees it. Unknown, missing or oversized
  section/username → 400; the `skills` list is capped at 64 ids; a thrown park error is the
  only 500. The Desk sends `rosterClient.current().section`, so real traffic is unchanged.
- Test: `railway-server/tests/park-calc-read-routes.test.js`.

## Confirmed by reading, not fixed here (needs a design decision)

### 2. Live Classroom identity is a bare claim; the park and the bonus rail trust it

- Where: `railway-server/server.js` `case 'classroom_join'` (line 3915; section, username and
  `role: 'teacher'` taken verbatim from the WebSocket packet; no roster token is read —
  `verifyToken` from `token.js` is used only by the HTTP `sidFromRequest`). The Desk's
  `classroom-board.js sendJoin()` indeed sends only `{section, username, role, hue}`.
- Consequence for the routes in scope: `shared-classroom.mjs createParkRegistry._wsEntry`
  derives the park identity from that join, so any client can play solo calculator rounds
  as any username. A clean solo clear at rung 2, or a passed handheld check
  (`calculator-service.mjs receiveHandheld`), flips `park_calc_srs.mastered` for that
  username and `calculator-bonus.mjs post()` banks a bonus row for them on roster-server
  (`POST /class/bonus`, grade I, additive, one per skill forever). The spoofer can also earn
  and spend campaign keys for another student, and — by playing messy rounds — move another
  student's hint rung (see "checked" below: rung movement is by design, but it should be the
  student's own). A self-declared `role: 'teacher'` also passes the teacher-only WS checks
  (`calculator_recognition`, the class-sound switch `classroom_sound_set`, `park_watch`
  spectator state of every student's attempt).
- Why not fixed here: the fix is a protocol change, not a minimal diff — `classroom_join`
  would carry the roster token (the Desk already holds one for the HTTP routes), the server
  would verify it with `verifyToken` and take `username`/`section`/`role` from the token,
  and every WS client (Desk board, teacher classroom, park smoke scripts) would need the
  field. The teacher's standing decision that Live Classroom is shelved and the park is
  "no grade writes" (the bonus row is additive and only banks at quarter close) keeps the
  blast radius small, but the bonus rail did turn the park into a credit-adjacent writer on
  2026-10-15 (`9d41cd7`). Recommend: token-on-join, with a `log` mode first like
  `AI_GRADE_AUTH`.

## Plausible, could not confirm

- **Section state is also unbounded over the WebSocket.** `classroom_join` with any
  section string (finding 2) → `createSoloRound` → `clears.ensure / srs.ensure /
  wallet.ensure` (`calculator-service.mjs` 166) create the same permanent section entries
  and store loads as finding 1 did over HTTP. Not fixed because the park tests use sections
  outside the allow-list (`PeriodC`, `P`), and `classroom.js getOrCreateRoom` (line 840)
  deliberately accepts any section; the classroom rooms themselves are GC'd by `sweep()`
  (line 1278) but the clears/srs/wallet `sections` Maps are never pruned. Closing this
  properly is the same decision as finding 2.
- **Deploy-overlap lost update on the absolute upserts.** `calculator-clears-store.mjs
  save()` (line 41) and `calculator-srs-store.mjs save()` (line 50) write whole rows from
  process memory, on the assumption the relay is the single writer. During a Railway
  deploy the old and new instance can overlap for a few seconds; a clear recorded on the
  new instance can be overwritten by the old instance's last flush (its memory never saw
  it). Unconfirmed: no `railway.json`/`railway.toml` in the repo pins replicas or the
  overlap policy, and the window is seconds. The key grant path is immune (RPC
  transaction, `park_campaign_grant_key`), and `campaign-wallet.mjs setBought` already
  takes the max; the clears/srs rows could do the same (`GREATEST` in the upsert, or a
  `mastered OR` merge) if an overwrite is ever observed.
- **`AI_GRADE_AUTH` defaults to `off`, and `off` skips the rate limiter too.**
  `ai-grade-auth.js normalizeAiGradeAuthMode` (line 98) returns `off` for an unset env var,
  and `aiGradeAuth` returns `next()` before either quota window (line 394). Byte caps still
  apply. Whether production sets `log`/`enforce` is an env question I cannot read from the
  repo; `/health` reports `aiGradeAuth` — check it.
- **`/api/ai/grade` may 500 on a malformed `scenario`/`answers` shape.** `server.js` 1018:
  only `!scenario || !answers` is checked; `buildDefaultGradingPrompt` and `applyWrongMcqCap`
  (`receipts.js`) then read fields off whatever arrived. A TypeError lands in the catch at
  line ~1057 as `err.statusCode || 500`. Could not produce a concrete 5xx input by reading
  (`Object.values(7)` is `[]`, string scenarios index as `undefined`); worth a fuzz if the
  logs ever show `AI grading error: Cannot read properties`.
- **`calculator-bonus.mjs posted[]/failed[]` grow for the life of the process** (line 21).
  Bounded in practice by the number of masteries, and the sweep script
  (`railway-server/scripts/park-bonus-sweep.mjs`) is the recovery path; noting only because
  a process that runs for months with a flapping roster-server would keep every failure.

## Checked, no finding

- **Nothing lowers earned credit.** `calculator-srs.mjs advance()` spreads the previous
  record, so `mastered` is never cleared; `srs.master()` only sets it. The SM-2 reset of
  `repetitions` on quality < 3 is the schedule, not credit. `calculator-clears.mjs
  clearDelta()` can move a hint rung down (messy clear holds, rough clear at rung 2 drops to
  one clear) — that is ABSORB_2_SPEC §3 by teacher decision, a hint level rather than a
  grade, and `record()` floors at 0. `campaign-wallet.mjs open()` spends a key by design;
  `setBought` only grows. The bonus row is grade I, upserted at attempt 1 on roster-server
  (a repeat is a no-op), never re-posted lower. `applyWrongMcqCap` caps the AI's *verdict*
  for a wrong MCQ (rule, not a stored grade) and leaves `exceptionGranted` alone.
- **`POST /park/campaign/keys/grant`** (`campaign-key-grant.mjs`): timing-safe shared secret,
  503 when unconfigured, `receiptId` regex + length caps, idempotent on receipt through the
  RPC, 400/403 for bad input and 503 only for store trouble. Clean.
- **AI grade routes** (`ai-grade-auth.js`): per-route body/prompt/answer byte caps parsed
  before auth, 413 on overflow, sid + IP rate windows with bounded key maps, batch capped at
  8 items (`server.js` 1098).
- **`/api/ai/appeal` "understanding" lifecycle** (`runUnderstandingReview`, `server.js`
  ~2349): sign-in required (401), question id regex, MCQ-only (400), eligibility 403s, 409
  on a duplicate exchange, 3-word minimum; grants are HMAC-signed rows. The legacy appeal is
  refused for canonical MCQ items.
- **Park WS input bounds:** campaign `bits` 0..1023, `from/frame` integer-ranged, event
  pages of 500, room caps 64 (campaign) / 128 (park), log restart at 20 000 entries; calculator
  poses range-checked, `clientId` regex, handheld values sliced to 3 fields, `skills`
  resolved through the catalogue.
- **Read-modify-write within one process:** every room/attempt/wallet mutation runs on the
  single event loop with no `await` between read and write; the only async writes are the
  store flushes, which serialise per section (`saving` flag) and re-dirty on failure.
